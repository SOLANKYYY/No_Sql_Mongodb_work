# Reduced workload and source semantics

This revision uses up to 15,000 real indicator observations, with a minimum of 1,000 so each 1,000-write trial has sufficient input. It is a user-requested departure from the assignment requirement of 100,000 records. Report the actual measured count, not the original target.

For MISP exports, one row is an indicator attribute UUID. Several rows can belong to one event. Source is the reporting organization; target is the reported observable (not a victim); timestamp is the attribute modification time (not an attack time). Spread means shared observables across publishers, and daily counts measure feed modifications. Communities indicate overlapping publisher claims, not confirmed fraud or false positives.

# Comparative methodology
## Scope
The assignment screenshot asks for 100,000 threat records across MongoDB, Cassandra and Neo4j; this user-requested revision instead uses up to 15,000 indicator observations. This supersedes the smaller MongoDB-only financial-transaction sample in the reference repository. All three backends are required; no estimates replace missing measurements. Source data comes from the user's export/API, not a generated feed. Selection uses the up to 15,000 most recent unique supplied events, preserving timestamps, fields and dataset checksum. Invalid or conflicting records fail rather than silently disappearing.
## Schemas
MongoDB: full_threats has one event per document. threat has one source document with only its latest 50 events (bounded array). Compound indexes support source history, target spread and UTC-day analytics.
Cassandra: threats_by_source partitions by (dataset,source), clustered by timestamp and ID descending. threats_by_type partitions by (dataset,type,day). threats_by_target and threats_by_day are additional query-oriented tables; all four denormalized writes count toward ingestion cost. Single-node replication factor 1 is for the lab only. At scale, source history must be day-bucketed to bound partitions, with a multi-day merge for history reads.
Neo4j: Source-REPORTED->Threat-TARGETS->Target with unique composite string keys scoped by dataset. SUSPICIOUS source relationships are derived from at least two shared targets. Source IDs in this project mean reporting sources, not automatically malicious actors.
## Fairness
History returns the same 50 IDs, spread returns the same distinct sources for one target, daily analytics returns the same UTC-day counts. Outputs must match Python truth derived from the export on every run. One warm-up precedes ten measured read runs per workload; backend order rotates. Ingestion uses 1,000 events per trial, ten trials, in separate namespaces and includes all schema-maintenance writes. Read latencies include full result consumption. Cassandra daily aggregation includes transfer and client-side counting, because CQL is not a general GROUP BY analytics engine. MongoDB/Neo4j aggregate server-side. This intentional modeling difference is disclosed, not hidden.
The ten writes use copied event fields with new IDs only as a controlled throughput fixture; they are excluded from baseline reads and not represented as additional real feed records. Results report median, minimum, maximum and all ten samples. Ingestion events/sec is 1000 divided by median batch duration. This measures batch ingestion, not a continuously operating real-time feed.
## Durability and resources
One node per engine, same Docker host, default classroom durability. MongoDB w=1, Cassandra LOCAL_ONE and Neo4j committed transactions are not equivalent replicated guarantees. Database startup/load is excluded from read timings; ingestion load time is separately reported. Warm caches, client serialization, host contention and different memory limits affect outcomes. Compare this particular configuration only; rerun with controlled resources and matched durability before production selection.
## Graph activity
Read target-to-source adjacency from live Neo4j; project weighted source edges (two or more shared targets), find greedy modularity communities with NetworkX, write SUSPICIOUS edges back into Neo4j, and select communities with >=3 members and density >=0.5. Targets with >100 sources are skipped to prevent quadratic hub expansion; the skipped count is reported. Cross-reference each candidate community with MongoDB original event counts and repeated indicators. This is an external graph algorithm on a Neo4j-derived graph, not a claim that Neo4j GDS ran. Dense connectivity can reflect benign syndication or real attacks. Without ground-truth labels, precision/recall of false-positive detection is not claimed.
## Operations
MongoDB: practice tested backups/restores and monitor replication, storage/index size and query plans. Cassandra: snapshot plus commit-log strategy, regular repair and compaction/tombstone monitoring; model access patterns before ingestion. Neo4j: consistent backups (edition-dependent online tooling), graph/page-cache/transaction monitoring and restore drills. Monitor ingestion lag and provenance quality across all engines. Production deployments need authentication, TLS, access controls and tested recovery objectives; this isolated local lab exposes no DB ports to the host.
## Scaling (design estimates, not measured results)
MongoDB distributes data through sharding; choose a key that avoids hot ranges and fits routing. Cassandra distributes partitions by token and replication; bucket hot source/day partitions. Neo4j 5.26 Community used here is not a distributed write cluster; production graph scaling/HA needs an appropriate edition/deployment and verification of its supported architecture. Read replicas do not imply linear write scaling. No 1M/10M/100M benchmark is claimed.
Sizing illustration only: assume 1 KiB logical event, MongoDB 2x space including indexes, Cassandra 4 query copies x 1.5 overhead, graph 4x space, 3 physical copies, and 30% free-space reserve. Formula disk = N*1024*factor*3/0.7. Actual compression, cardinality and graph edges change this substantially. CPU/RAM estimates in the report are initial load-test budgets, not guaranteed requirements or vendor specifications.
